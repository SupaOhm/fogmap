# Milestone 1 design: solo fog map

Status: approved in brainstorming on 2026-10-28.
Requirements: [docs/milestone-1.md](../../milestone-1.md). This document records how they will be built and every decision that refines or changes them.

## Changes to the milestone spec

| Milestone spec says | Design decision | Why |
|---|---|---|
| Efficient mode uses `Balanced` accuracy | Efficient uses `High` accuracy; savings come from a larger distance interval and auto-pause | On iOS, `Balanced` maps to ~100 m accuracy, which conflicts with the 50 m accuracy filter and would drop many fixes |
| In-memory buffer holds raw coordinates | Previous point is `{ cell, ts, lat?, lng? }`; only `cell` and `ts` persist | Gap filling and the speed check survive iOS killing the app, with no coordinates on disk |
| Debug screen in dev builds only | Debug screen gated by a build-time flag, on by default for M1 | Field tests run Release builds (JS bundled in), which would otherwise hide the screen |
| `track_log(ts, accuracy, speed, accepted, battery)` | Adds `reject_reason` and `tracking_mode` | Battery per hour per mode needs the mode; reject reasons make filter behaviour visible |
| `cells.mode` unspecified on revisits | Stores the slowest speed bucket ever seen | Keeps the data needed to exclude driving later |

## Environment

- iPhone builds are made locally with Xcode 27.1 and a **free Apple ID** (installs expire after 7 days).
- Daily work: `npx expo run:ios --device` (Debug, loads JS from Metro).
- Field tests: `npx expo run:ios --device --configuration Release` (JS bundled), because a background relaunch away from the Mac cannot reach Metro.
- `ios/` and `android/` are generated by `expo prebuild` and not committed. All native config lives in `app.config.ts`: expo-location and MapLibre plugins, `UIBackgroundModes: location`, permission strings, `ios.appleTeamId`, bundle ID `com.supaohm.fogmap`.
- Library versions are checked against the current Expo SDK at install time, not taken from memory.

## Core logic (`src/core/`)

Pure TypeScript, no React or Expo imports, fully unit-tested with Jest.

**Live tracking and GPX import both call `processFixes`**, so imported routes reveal cells exactly as live tracking would.

| File | Responsibility |
|---|---|
| `constants.ts` | `H3_RES = 10`, `REVEAL_RADIUS = 1`, `MAX_ACCURACY_M = 50`, `MAX_SPEED_KMH = 300`, `GAP_MAX_M = 2000`, `GAP_MAX_MS = 600_000`, `WALK_MAX_KMH = 8`, `CYCLE_MAX_KMH = 25` |
| `types.ts` | `Fix { ts, lat, lng, accuracy, speed: number \| null }`, `SpeedBucket = 'walk' \| 'cycle' \| 'vehicle'`, `LastPoint { cell, ts, lat?, lng? }`, `RejectReason = 'accuracy' \| 'invalid' \| 'stale' \| 'speed'`, `RevealedCell { bucket, firstTs, lastTs }` |
| `filter.ts` | `evaluateFix(fix, prev)` returns `{ accepted: true, bucket }` or `{ accepted: false, reason }` |
| `reveal.ts` | Fix to cell; gap fill from the previous point with `gridPathCells` when under `GAP_MAX_M` and `GAP_MAX_MS`; expand every path cell with `gridDisk(REVEAL_RADIUS)` |
| `pipeline.ts` | `processFixes(fixes, lastPoint)` returns `{ cells: Map<h3, RevealedCell>, logRows, nextLastPoint }`; `firstTs`/`lastTs` are the earliest/latest fix times that revealed the cell, so the database sets `first_seen`/`last_seen` from fix time, not wall-clock time |
| `stats.ts` | Area as the sum of `cellArea` (km²); today / this week / all-time windows using local midnight and a Monday week start; battery %/hour per tracking mode, ignoring intervals where the level rose (charging) |
| `fog.ts` | `buildFog(cells)` returns GeoJSON: a world-covering polygon with the revealed area (`cellsToMultiPolygon`) as holes |
| `gpx.ts` | Parse a GPX string into `Fix[]` with accuracy 5 m and `speed: null`; when timestamps are missing, synthesize them at walking pace (5 km/h) |
| `stress.ts` | Generate N cells along a random walk, for the rendering benchmark |

**Fix checks, in order** (amended after the Plan 1 final review, 2026-10-28):
1. `accuracy`: rejected unless accuracy is finite and between 0 and 50 m (on iOS a negative accuracy means the position is invalid).
2. `invalid`: rejected unless lat/lng are finite and in range.
3. `stale`: rejected when older than the previous accepted point (iOS can resend cached fixes).
4. `speed`: only when the gap from the previous point is **under 10 minutes**. Longer gaps are never filled, and checking them would reject every fix for hours after a flight.

**Speed check distance.** With `lat`/`lng` in memory, use the real distance. When only the persisted cell is available (after a relaunch), use the lower-bound distance (cell-centre distance minus the cell's maximum centre-to-vertex distance, floored at 0), so a real fix is never rejected because of cell imprecision.

**Speed bucket.** Use the fix's reported speed when it is valid (`>= 0`), otherwise the speed computed from the previous point (only within the 10-minute window), otherwise **`vehicle`**. Unknown speed takes the fastest bucket because a cell keeps the slowest bucket it ever had, so any later slower visit can still correct it. Gap-filled cells take the bucket of their segment.

**Tests cover at least:** first fix with no previous point; gap exactly at each limit; a jump over the limits (no fill); the antimeridian; invalid reported speed; runs of rejected fixes; relaunch with a cell-only previous point; slowest-bucket merge; GPX with and without timestamps; battery rate with a charging interval.

## Tracking (`src/tracking/`)

- The location task is defined with `TaskManager.defineTask` at the top level of the entry file, so it exists when iOS relaunches the app in the background.
- The task handler for each batch:
  1. loads the previous point from memory, or from `settings` after a relaunch;
  2. calls `processFixes`;
  3. writes everything in one exclusive transaction: cell upserts, `track_log` rows (with the battery level from `expo-battery`), the new previous point;
  4. catches every error, stores the last error message, timestamp and an error count in `settings`, and never throws.
- After a commit, the task emits an in-process event so an open map can refresh.

**Modes** (stored in `settings`; switching restarts location updates):

| | Accuracy | `distanceInterval` | `pausesUpdatesAutomatically` | `activityType` |
|---|---|---|---|---|
| Efficient (default) | `High` | 50 m | true | `Other` |
| Precise | `Highest` | 10 m | true | `Other` |

`showsBackgroundLocationIndicator: false` in both. All values are constants, so they can be tuned after the field test.

**iOS risk, checked first in build step 5:**
- iOS does not resume automatically paused updates in the background.
- Standard location updates do not relaunch a terminated app.

Read expo-location's native iOS code to see whether it handles either case. If not, add a geofence (via `startGeofencingAsync`) around the last cell's centre; exiting it wakes the app and restarts updates. iOS holds the geofence, so nothing is written to our disk. If reliable background reveal is still impossible, stop and report back.

**Permissions.**
- Request "When In Use", then explain and request "Always".
- Without "Always", tracking works only in the foreground and the Map screen shows a banner.
- At launch, reconcile the stored on/off setting with the registered task and the current permission.

## Storage (`src/db/`)

- One shared `expo-sqlite` connection for the UI and the task, WAL mode.
- Schema version in `PRAGMA user_version`, ordered migrations.

```sql
cells(h3 TEXT PRIMARY KEY, first_seen INTEGER, last_seen INTEGER, visit_count INTEGER, mode TEXT)
track_log(ts INTEGER, accuracy REAL, speed REAL, accepted INTEGER, reject_reason TEXT, tracking_mode TEXT, battery REAL, charging INTEGER)
settings(key TEXT PRIMARY KEY, value TEXT)
```

- Cell upsert from `RevealedCell`: insert with `first_seen = firstTs`, `last_seen = lastTs`; on conflict set `first_seen = MIN(stored, firstTs)`, `last_seen = MAX(stored, lastTs)`, increment `visit_count`, and set `mode` to the slower of the stored and new bucket (this is where the slowest-bucket rule holds across batches).
- `visit_count` counts **batches that touched the cell**, not distinct visits. It is diagnostic only; nothing in M1 depends on it.
- `charging` comes from `expo-battery`'s battery state. `batteryRatePerHour` must skip any interval where either end was charging (otherwise a night on the charger counts as zero drain).
- The previous point is written only through a branded `StoredPoint` type (`{ cell, ts }` produced by `persistable()`), so a `LastPoint` with coordinates cannot be passed to the settings writer by accident.
- `track_log` rows older than 7 days are pruned at launch and at most once a day by the task.
- `settings` keys: `tracking_enabled`, `tracking_mode`, `last_point`, `last_error`, `last_error_ts`, `error_count`, `last_prune_ts`.
- No table has coordinate columns.

## Screens (`src/screens/`, `src/map/`)

Bottom tabs with expo-router: **Map**, **Stats**, **Debug** (Debug only when the build flag is on).

**Map**
- MapLibre with an OpenFreeMap style, picked during scaffolding from the styles currently published; the style URL is a constant, and MapTiler is the fallback.
- Fog: `buildFog` output in a ShapeSource drawn by a dark FillLayer (~0.8 opacity), plus a blurred LineLayer on the same shape for a soft edge, dropped if it looks wrong.
- Refresh on the tracking event and when the app returns to the foreground, debounced so `buildFog` runs at most once every 2 s.
- Follow-me button using MapLibre's user location and camera follow (foreground only, separate from tracking).
- Tracking on/off toggle, km² chip, banner when "Always" is missing.

**Stats.** Cell count and km² for today, this week and all-time. "Revealed" means `first_seen` falls in the window.

**Debug**
- Efficient / Precise switch.
- Today's fixes received, accepted, and rejected by reason; last fix time and accuracy; last error and error count.
- Battery samples and estimated %/hour per mode.
- Last `buildFog` duration and cell count.
- GPX import (`expo-document-picker`, then `gpx.ts`, then `processFixes`, then the same **cell** writes as the task). GPX import runs with `lastPoint = null`, never saves its `nextLastPoint` as the live previous point, and never writes to `track_log`. Otherwise live tracking would reject fixes against the route's (possibly future) timestamps, and battery stats would be corrupted. Synthetic GPX times are placed so the route ends at the import time.
- Stress fill with N cells (default 50,000).
- Reset all data, with confirmation.

## Fog performance

Use option A: rebuild the whole fog shape (debounced, foreground only). Expected real M1 use is a few thousand cells.

If the on-device stress test at 50,000 cells is not acceptable, switch `buildFog` internally to chunking: group cells by a coarse parent cell, cache each group's outline, rebuild only touched groups. Callers do not change.

**Measured baseline (2026-10-28, iPhone 14, Debug build, Hermes):** `cellsToMultiPolygon` on 7,651 cells took **3,110 ms** (Node: ~240 ms for 51,000 cells). Debug Hermes is slower than Release, so Plan 2 must measure `buildFog` in a **Release** build early, before the map screen depends on it. If 50,000 cells take more than ~1 s in Release, implement chunking in Plan 2 rather than later.

## Verification

| Acceptance criterion | How it is checked |
|---|---|
| Unit tests pass for `src/core/` | `npm test` |
| 50 km GPX reveals a corridor with no gaps | GPX import on device, visual check |
| Smooth panning with 50,000+ cells | Stress fill, then pan; `buildFog` duration on Debug |
| 30-minute locked walk reveals the route | Field-test checklist |
| Tracking resumes after iOS kills the app | Field-test checklist (or a documented limitation) |
| No raw coordinates on disk | Schema and pipeline-output tests; manual: download the app container in Xcode and search the SQLite file (field-test checklist) |
| Battery per hour per mode | Debug screen estimate after a day in each mode |

**h3-js under Hermes** is verified in build step 1 with a temporary on-device check of `latLngToCell` and `cellsToMultiPolygon`. If it fails, stop and report before choosing an alternative.

## Path to production (not built in M1)

- `src/core/`, the `cells` table, tracking config and permission flow carry over unchanged.
- Sync adds a column (for example `synced_at`) via a migration.
- Coarser sharing cells come from `cellToParent`.
- Production builds turn the Debug flag off.
- Later milestones need:
  - a paid Apple Developer account (TestFlight / App Store);
  - an App Group container for widgets, reached by a one-time migration that moves the database file (not available with a free Apple ID);
  - a strong justification for "Always" location in App Store review.
- **Cell resolution is the one irreversible choice:** coarser views can always be derived, finer ones cannot be recovered. Settle it during the M1 field test.
